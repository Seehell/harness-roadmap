# ADR-0001：先关闭前端并保留 Rust CLI 核心

- 状态：已接受
- 日期：2026-11-21
- 决策范围：第一阶段架构与开发顺序

## 背景

项目处于纯新手探索阶段，同时使用 Termux 中的 DSH，并希望用 Rust 自研 Harness。开发前端、Rust 核心、Agent、存储和终端能力会显著增加同时需要解决的问题。

## 待选方案

### 方案 A：同时开发前端与后端

优点：

- 产品可视化更早
- 容易演示交互

代价：

- 同时需要解决 UI、协议、状态、进程和 Agent 问题
- UI 往往反向绑定核心接口
- 开发和排障范围增加

### 方案 B：先实现 Rust CLI 核心，暂时关闭前端

优点：

- 主流程更快闭环
- 便于 Termux 环境验证
- 核心接口更容易保持独立
- 前端可后续替换

代价：

- 前期没有图形界面
- 部分状态只能通过日志和命令查看
- 多步骤操作需要在终端完成

### 方案 C：完全复用现成 Harness，暂不自研

优点：

- 能最快获得完整功能

代价：

- 不满足 Rust 自研目标
- 对现有实现和协议的理解不足
- 后续替换成本可能较高

## 决策

采用方案 B。

第一阶段使用 Rust CLI 和 DSH 组合，保留一个可替换的 Agent 接口和任务持久化能力。暂缓独立前端开发，但不删除将来的前端接入能力。

## 自研与复用边界

自研：

- Harness 核心任务生命周期
- 本地任务状态与日志组织
- Agent 抽象与适配器
- 面向当前需求的命令行接口

复用：

- DSH 及现有终端能力
- Rust 工具链和生态库
- SQLite 或成熟存储库
- 成熟 Agent API 或 SDK

## 代价

- 短期缺少可视化界面
- 必须维护部分 CLI 交互
- Rust 依赖和编码门槛需要逐步学习

## 复核条件

满足以下任一条件时重新评估前端：

- CLI 已无法满足明确的操作需求
- 用户要求可视化状态或任务控制
- 核心状态接口稳定且有明确前端方案
- 成熟前端接入成本低于继续扩展 TUI
